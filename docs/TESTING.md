# Test strategy

Tests must use generated/synthetic data only. Required evidence: policy matrix and exclusions; private-by-default and new-chat behavior; credentials/rotation/revocation; account isolation and IDOR; pre-authorization of every batch target including forwarding sources; per-item failure outcomes; known-rejected retry-after and unknown write outcome handling; session failures; audit secrecy and retention; API, CLI, MCP, panel and end-to-end tests; PostgreSQL migrations and recovery where an isolated server is available. Test allow and deny paths for every interface. Tests may not be disabled or weakened to obtain a green run. Exact executed commands and unavailable dependencies are recorded in `STATUS.md`.

The suite includes an actual headless Chromium workflow for the owner panel (including stored-XSS negative checks and narrow viewport), official MCP SDK Streamable HTTP and stdio subprocess clients, CLI/API authorization tests, and temporary Unix-socket PostgreSQL integration. Install the Python and Node development dependencies in `DEVELOPMENT.md` before running the whole suite. No tests use live Telegram.

The backup/restore integration uses a disposable PostgreSQL server and verifies wrong keys, ciphertext tampering, non-empty targets and archive traversal rejection. An optional native TDJSON probe is skipped unless `TG_TDLIB_LIBRARY` points to a locally built library; on Linux the probe installs a seccomp filter denying network syscalls before loading the library, uses no parameters or credentials, and closes both empty clients. This feasibility test is not a live Telegram test.
