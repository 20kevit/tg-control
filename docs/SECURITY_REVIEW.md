# Security review and release blockers

Review date: 2026-11-06. Scope: this repository's synthetic-only gateway, interfaces, optional synthetic storage and backup utility. This is an internal engineering review, **not** an independent penetration test, legal advice or approval for production/real Telegram. No real content or credentials were used.

## Controls exercised

- **Identity and authorization:** owner/client tokens are separate; independently random client bearer tokens are stored only as digests, rotated/revoked; account assignment and Read/Write/Admin are independent. Exclusions win, private chats require explicit IDs, forwarding needs source Read and destination Write. Gateway, HTTP, MCP, CLI and browser negative tests exercise these boundaries. Host/Origin validation, duplicate/framing-header checks and streamed body-size limits for every HTTP method precede routing; boundary rejections and authenticated decisions are audited without raw headers or bodies. Health and OpenAPI schema endpoints also require credentials and are audited.
- **Effects and failure:** all batch targets are authorized before effects; item results are not atomic. Mutation keys are durable and single-use; definitive rate-limit retries honor reported delays and reauthorize. Timeouts or post-effect errors may leave unknown outcomes. Audit start/decision failure blocks effects; audit completion can fail after the effect and is reported only as a sanitized operational error, so monitor it.
- **Untrusted data:** no incoming message is executed as an instruction. Panel content is created using text nodes and restrictive CSP; headless Chromium checks a synthetic stored-XSS payload. Owner tokens stay in memory; logout, a 15-minute idle lock, and a rejected owner credential clear the UI state. In-flight responses are rejected after session changes. A one-time client credential is shown before refreshing data, including when refresh fails.
- **Storage:** phone metadata and optional per-account synthetic state are authenticated-encrypted; per-account keys are HKDF-derived and state paths are UUID-derived. Files and secrets use restrictive permissions; POSIX locking rejects concurrent use of a state directory. Memory cache is bounded, reauthorized on access and invalidated on writes. Synthetic media expiry is enforced and tested; filesystem snapshots/backups are not securely erased by expiry.
- **Backups:** AES-256-GCM archives authenticate before parsing; restore accepts only regular files with expected UUID-derived paths and refuses existing state directories and detectable non-empty database targets. The preflight catalog probe and `pg_restore` use the same private libpq service in isolated child environments; the probe fails closed if inspection fails. This is defense in depth, not proof of a new/empty target or protection from concurrent writers. An isolated PostgreSQL test verifies restoration and rejects wrong keys, tampering, a live state lock and path traversal. Backup/restore use private plaintext scratch files; a private tmpfs and careful swap/core-dump management are essential. DB and files cannot be restored atomically together.
- **Dependencies:** Python runtime/build packages are pinned with hashes in `requirements.lock`; an isolated clean install, package/static asset checks and `pip check` passed. The pinned Python lock was checked with `pip-audit` using PyPI advisories; npm's locked browser-test dependencies were checked with `npm audit`. No known advisories were reported at the time of this review. Bandit reported no medium/high findings; four low subprocess findings were reviewed: trusted PostgreSQL binaries and an isolated Python probe are invoked without a shell, with a minimal environment and suppressed diagnostics. Binary provenance and local executable selection remain the operator's responsibility. These checks are not proof of absence of vulnerabilities and do not assess base-image/OS packages.

## Open findings and residual risk

1. **Release blocker: compliance and real adapter.** Telegram's terms create an unresolved gate. No native/live adapter, consent-withdrawal workflow, real account authorization, protected/self-destructing-content handling or sponsored-message support is implemented. Do not change this gate by configuration or use real data. An offline, network-syscall-blocked TDJSON ABI probe passed, and unwired synthetic schema models screen visibility/text flags and send outcomes; these are not an adapter, protected-content enforcement, legal clearance or a live implementation.
2. **Remote identity/transport:** remote MCP uses static bearer headers, not OAuth discovery/authorization; ChatGPT remote compatibility is unverified. Bearer credentials can be replayed if stolen. There is no owner MFA, token expiry or application-level authentication rate limiting. The static owner login/bootstrap assets are currently unauthenticated and must remain local-only; any future approved remote deployment needs authenticated ingress for those assets as well, TLS, restricted ingress, independent identity/abuse controls and a fresh security review.
3. **Operational hardening:** container builds, image digest pinning and OS/image scanning are unverified; no production-grade secret manager, automated backup verification, alert delivery, clustered cache/state coordination or high-availability strategy exists. Use only one process/instance and do not expose the development environment publicly.
4. **Retention and recovery:** media cleanup occurs at access/startup and about hourly while online, not during downtime. Audit pruning is a deliberate owner action; authenticated periodic health checks also create audit rows and can increase storage use. Backups/snapshots may retain old data and key rotation for encrypted existing state is not implemented. A restored backup may reactivate older credentials/policies; rotate and review after recovery. Backups use plaintext temporary scratch and restore is not atomic across DB/files.
5. **Concurrency and observability:** read results are rechecked immediately before delivery, but policy/credential changes cannot retroactively cancel an already in-flight external mutation or a response already sent. Logs are intentionally sanitized, which limits diagnosis; monitor audit/maintenance failures and resource exhaustion. In-memory cache can serve authorized stale reads within its TTL. No distributed tracing, owner push alerts or SIEM integration exists.
6. **Supply chain:** pinned package hashes reduce dependency drift, but builds rely on Python/package registries and mutable base-image tags; no signature verification or SBOM/image vulnerability scan is completed. Development browser binaries and any optional native build have their own trust boundary.

Reassess these findings, current upstream advisories and Telegram terms before any release. Do not claim this implementation is secure for real accounts or complete until outstanding gates and independent validation are resolved.
